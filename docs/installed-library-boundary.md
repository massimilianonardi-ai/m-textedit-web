# Installed library boundary: finding and proposal

Status: investigated, not implemented in m-os. `pkg` v2 validates only `link/lib/sh` and `link/lib/java`; `_pkg_integration_libraries_validate` rejects other kinds, and `_pkg_integration_v2_validate_definition` requires link/bin, facility-bin or link/lib. A pure JS library with only a facility-env directory is therefore not an accepted v2 package definition. Do not add dummy commands or shell/Java files to bypass this check.

Recommended next design: extend the existing typed library export mechanism with `link/lib/js/<name>.js`, validating a root-contained readable JS artifact and materializing it in the versioned package. Use the existing facility compatibility/dependency and facility-env projections to provide explicit selected package asset roots to consumers, without introducing an automatic runtime loader or source fallback. Keep JS browser delivery under the web host and Electron host; do not equate Node module search paths with browser URLs. Verify context provider/version semantics, typed-export security and compatibility of existing sh/java exports before product changes. A separate contract decision is still needed before changing pkg, context or the catalog. Current code already takes explicit engine and GUI asset roots, so no change to TextEdit editing semantics should be required.
